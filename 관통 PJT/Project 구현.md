# 관통 PJT Project 구현 정리

지금까지 진행해 온 관통 프로젝트 전체 과정을 되돌아보는 **Summary/Overview**, 실제 협업에서 사용하는 **명세서**의 역할, 그리고 팀 프로젝트를 끝까지 완주하기 위한 **프로젝트 관리 및 진행 방법**을 정리한 문서입니다.

---

## 1. 관통프로젝트 Summary_Overview

관통 프로젝트는 아래와 같은 흐름으로 하나의 서비스를 처음부터 끝까지 완성해보는 과정이었습니다.

```
데이터 수집(Git/파일시스템/JSON/API)
  → 데이터 전처리 및 가공(생성형 AI, gTTS, MCP)
  → 반응형 웹 UI 구현(Web Font, Figma, AI 코딩)
  → 인증 기능 구현(세션/JWT)
  → 관계형 DB 모델링 및 정규화
  → 협업 워크플로우(Git Branch/Merge)
  → 프론트엔드 상호작용(DOM 이벤트) 및 데이터 분석(문서 유사도)
  → AI Agent/MCP를 활용한 지능형 기능
  → 위치 기반 서비스(지도 API) 구현
```

* 각 단계는 독립적인 기술 학습이 아니라, **하나의 서비스를 완성하기 위한 유기적인 흐름**이라는 점이 관통 프로젝트의 핵심 의도

---

## 2. 명세서 소개

### 명세서가 필요한 이유

* 팀원 간 "내가 생각한 기능"과 "상대가 생각한 기능"이 다르면 프로젝트 후반부에 큰 혼선이 발생 → 문서로 합의된 기준을 남겨두는 것이 명세서의 역할

### 대표적인 명세서 종류

| 명세서 | 내용 | 주로 참고하는 사람 |
| --- | --- | --- |
| **기능 명세서** | 각 기능의 동작 조건, 예외 처리 방식 | 팀 전체 |
| **API 명세서** | 엔드포인트, 요청/응답 형식, 상태 코드 | 프론트엔드 ↔ 백엔드 |
| **화면 명세서(와이어프레임)** | 화면별 구성 요소와 사용자 흐름 | 프론트엔드, 디자인 담당 |
| **DB 명세서(ERD)** | 테이블 구조와 관계 | 백엔드, DB 설계 담당 |

* 명세서는 한 번 작성하고 끝내는 것이 아니라, 개발 중 변경 사항이 생기면 **그때그때 갱신**해야 실제 협업 문서로서 의미가 있음

---

## 3. 프로젝트 관리 및 진행 방법 소개

### 일정 관리

* 전체 개발 기간을 **스프린트(Sprint) 단위**로 나누어, 각 스프린트마다 목표 기능을 정하고 완료 여부를 점검
* 매일 또는 격일로 짧은 **스탠드업 미팅**을 통해 진행 상황과 블로커(막힌 부분)를 공유

### 이슈/작업 관리

* Github Issues, Notion, Jira 등으로 **작업(Task)** 을 단위별로 쪼개어 담당자와 기한을 명시
* 작업은 "할 일 → 진행 중 → 완료" 같은 칸반(Kanban) 보드로 시각화해 전체 진행 상황을 팀원 모두가 파악할 수 있도록 함

### 코드 리뷰 문화

* 기능 브랜치에서 작업 후 Pull Request를 생성하고, 최소 한 명 이상의 팀원이 리뷰 후 병합하는 것을 원칙으로 함
* 코드 리뷰는 단순히 오류를 찾는 것뿐 아니라, 팀원 간 코드 스타일과 설계 의도를 공유하는 과정이기도 함

### 마무리 단계 체크리스트

1. 명세서와 실제 구현이 일치하는지 최종 확인
2. 주요 기능에 대한 시나리오 테스트(정상/예외 케이스) 수행
3. README, 발표 자료 등 프로젝트 산출물 정리

## 핵심 요약
* 관통 프로젝트는 데이터 수집부터 AI Agent, 위치 기반 서비스까지 각 단계를 유기적으로 연결해 **하나의 완성된 서비스**를 만드는 과정이었다.
* **명세서**(기능/API/화면/DB)는 팀원 간 기준을 맞추는 협업 문서로, 개발 중 변경 사항을 반영해 계속 최신 상태로 유지해야 의미가 있다.
* 프로젝트를 끝까지 완주하려면 스프린트 단위의 **일정 관리**, 칸반 보드 기반의 **작업 관리**, PR 기반의 **코드 리뷰 문화**가 함께 뒷받침되어야 한다.
